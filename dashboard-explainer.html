Databricks demo · visualizing massive data

Why Databricks Apps

For interactive visualization of massive data, a Databricks App does what classic BI tools like Power BI, Tableau and Qlik cannot. The example here is a fleet of EV batteries — the point is general.

The reasons

Five reasons it’s a Databricks App

Full fidelity

BI charts cap at a few thousand marks and sample the rest, so rare outliers vanish. The App renders every raw sample as a full-resolution picture.

Scales with the fleet

Add more vehicles and a BI extract keeps growing until loads and refreshes stall. The App queries bounded slices in the lakehouse, so response time stays flat as the fleet grows.

One platform to maintain

A separate BI tool is another system to license, secure, refresh and govern beside the lakehouse. The App runs on the data platform you already have — one place, one copy, one story.

Licensing you can save

Per-seat BI licenses recur for every viewer. A Databricks App serves users on compute you already run, avoiding a separate dashboarding subscription.

Interaction BI can’t do

It’s a real app: a lasso that triggers a server-side raw fetch, a sample-size control, a drill to one vehicle’s complete raw signal — none of it resident in the browser.

To see and interrogate massive data at full fidelity — not just chart a summary — a Databricks App is the right tool; a resident-extract BI tool is the wrong shape.

This is the evidence for a warranty claim or a field-quality report.

At no point is the raw signal thrown away. That is what makes the outlier findable — and, as the next tab explains, it is exactly what a resident-extract BI tool cannot do at fleet scale.

Tool comparison · Databricks Apps vs classic BI

Why this only works on Databricks Apps

The workflow needs two things at once: a full-resolution picture of hundreds of millions of raw samples, and the raw rows behind any selection on demand. Classic BI can’t do both at scale.

The root bottleneck

The wall is the rendering cap, not where the data lives

A chart can only draw so many marks — a few thousand — no matter how the tool is connected. To keep a billion raw points inside that ceiling, something must reduce them to a few thousand before they reach the screen. That reduction is where the outlier dies, and it happens in every connection mode.

Assume the server products (Tableau Server, Power BI Service, Qlik Sense Enterprise). Each connects one of two ways — pre-load a resident copy, or query the source live — and it is worth being precise about what sits in that copy, because the trap is the grain you load it at.

ToolPre-loaded — a resident copy on the serverDirectQuery / live — no resident copy
Tableau Server A published Hyper extract — the rows/columns you defined, at the grain you chose; scheduled refresh. Live connection: each interaction queries the source.
Power BI Service An Import model in the capacity’s in-memory VertiPaq engine (compressed columnar); scheduled refresh. DirectQuery: SQL sent to the source per interaction.
Qlik Sense Enterprise A QVF app loaded into the engine’s RAM (tables + associative symbol index); scheduled reload. Direct Query / ODAG: queries pushed to the source.

Why very large data is the bottleneck — the grain trap. Whatever the mode, you face the same fork, and both ends lose:

  • Load / query at raw grain (so you can see individual points): the resident copy becomes the size of the raw data — tens of GB to TB in RAM/capacity, with refreshes that scale with the data. It doesn’t fit and doesn’t scale. (DirectQuery avoids the copy, but the chart still can’t render a billion marks, so the query is forced to aggregate anyway.)
  • Load / query pre-aggregated (daily averages, percentiles): small, fast, scales fine — but the raw grain is gone, so the individual outlier is no longer in the data the chart can show.

So the resident copy’s size is a real operational cost only in the pre-load mode — DirectQuery removes it. But neither mode lets you see the raw outlier, because the rendering cap forces a reduction to a few thousand marks either way. That cap is the mode-independent wall.

The Databricks App does not hit that wall: it never renders raw points in the browser. It computes a full-resolution aggregate in the warehouse (a density that keeps the rare cell visible), and fetches raw rows on demand only for a bounded selection. No resident copy to size, and no few-thousand-mark ceiling on the overview.

The picture in one chart

Why massive data breaks classic BI visuals

A chart renders only so many marks — whether the data is loaded resident or queried live — so as the dataset grows, the fraction it can show shrinks, and it fills the gap by summarizing.

The wall is rendering: no chart draws a billion marks, so the data must be reduced to a few thousand before it’s shown — in every mode — and the outlier is what the reduction drops. (Pre-load mode adds a second problem — a resident copy that grows with the data — but DirectQuery removes that one and still hits the rendering wall.) The App sidesteps it: a full-resolution aggregate for the overview, raw rows fetched on demand for a bounded selection.

The conclusion

Why it can only be the Databricks App

One reason is decisive and mode-independent — fidelity. The others are real operational benefits, but they apply to the pre-load mode (DirectQuery avoids them), so they are the supporting case, not the core.

Fidelity — the decisive one

The chart’s few-thousand-mark cap forces BI to reduce a billion points to a summary in every mode, dropping the outlier. The App renders a full-resolution aggregate and fetches raw detail on demand.

Scalability

In pre-load mode, more vehicles = a bigger resident copy and slower refresh; DirectQuery trades that for a per-click round-trip. The App’s bounded queries stay flat.

Maintenance

No separate BI system to size, refresh and govern — it runs on the lakehouse you already have.

Licensing

No per-seat dashboard subscription; users are served on existing compute.

The raw data never leaves the lakehouse: a full-resolution aggregate for the overview, and a fresh bounded query for every drill. So a Databricks App sees the outlier and reaches the raw detail, stays fast as the fleet grows, and needs no separate BI tool to license and maintain.
